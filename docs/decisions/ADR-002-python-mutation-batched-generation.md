# ADR-002: Function-Granular Byte-Budgeted Batched Mutation Generation

## Status

Accepted

## Date

2026-06-23

- 2026-06-23: Accepted after design review.

## Context

mutmut 3's schemata model packs all mutants of a source file into one module. CPython's tokenizer is
super-linear (~O(n²·⁴)) in the size of a single `ast.parse`/`compile` call (profiled and reproduced in
[`docs/design-python-mutation-scalability.md` Appendix A](../design-python-mutation-scalability.md)): a
117 KB / 3100-line source → 6071 mutants → ~82 MB module that takes >40 min to parse and times out,
orphaning a 100%-CPU worker. An interpreter upgrade does not fix it (3.12/3.13/3.14 all time out); the
cost is single-core CPU, not memory.

The current full cap profile bounds this by `maxSelected` (1000), which **drops** mutants — lossy, and it
caps the wrong quantity (count, not generated bytes; §13.5). Measured chunking/splitting (§13.7) shows
the cost is quadratic in single-call size, so splitting one module into K smaller ones cuts total parse
to ~1/K (K=8: >2400 s → ~103 s) while keeping all mutants.

The pre-generation policy adapter (`_write_mutmut_generation_policy`) already controls which lines mutmut
materializes via `allowedLines`, and UTA already keys mutations by a global `opportunity_id` (ADR-001).

## Decision

Add a **`batch` generation strategy** to the Python3 mutation verifier, selected by a mode flag
(`python_mutation_generation_strategy`), **default `batch`** after node2 verification. `hard_cap` remains
available as the rollback strategy.

In `batch` mode:

1. Partition selected opportunities into **function-granular** batches by an estimated-generated-bytes
   budget (`python_mutation_generation_max_generated_bytes`, default **8 MB**, derived from the §13.7
   parse-cost curve). Generation is one-operator-per-selected-line (verified), so estimate per function =
   `(selected lines in function + 1) × function_source_bytes`; bin-pack First-Fit-Decreasing,
   deterministically. A `max_batches` guard bounds total wall time within the overall timeout; excess is
   trimmed by priority (`omittedByMaxBatches`) with a user-facing warning.
2. For each batch sequentially: clean the generated `mutants/` tree (preserve stats/coverage), write a
   batch-scoped generation policy (`allowedLines` = batch lines), run metadata generation (small module →
   ~1–2 s parse), build the per-batch candidate plan.
3. Aggregate per-batch plans into one `MutationCandidatePlan`: counts summed, survivors unioned,
   `candidatePlanId` fingerprint extended with the strategy, batch count, budget, and a deterministic
   partition signature.
4. A single function whose estimated bytes exceed the budget is handled by a **reason-coded cap/skip**
   (`omittedByGeneratedBytesCap`) this round; lossless intra-function split is deferred.

`batch` is lossless for all functions that fit the budget (the common case), keeps the ADR-001 contract,
and changes performance, not outcomes.

## Alternatives Considered

### Keep the count hardcap (status quo)

Pros: simplest; already shipped. Cons: lossy (drops mutants → possible false pass); caps count not bytes,
so it neither bounds module size reliably nor fixes the hang on a large single function. Rejected as the
sole mechanism; retained as the rollback strategy.

### Per-line batching

Pros: finest granularity, easiest even sizing. Cons: mutmut numbers mutants per-function per-generation
(`x_func__mutmut_1` resets each run), so splitting a function across batches makes the same tool-key
denote different mutations → aggregation conflation in raw-key fields (§13.9). Rejected in favor of
whole-function partitioning, which keeps each function's key series in one batch.

### Lossless intra-function split now

Pros: fully lossless even for a giant single function. Cons: requires batch-namespacing tool-keys and
merging on `opportunity_id`; more code and edge cases. Deferred — the over-budget single-function case is
rare and gets a reason-coded fallback this round.

### Patch mutmut to split its generated output / skip its validation parse

Pros: could help all mutmut users. Cons: forks/patches a dependency; the run-phase import-compile of the
whole module is still one parse. Rejected; UTA-side partitioning fixes both validation and execution.

### Upgrade CPython

Rejected: tested — `ast.parse` of the 82 MB module times out on 3.12.10, 3.13.3, and 3.14.0a7 alike
(Appendix A §13.4). No interpreter version escapes the single-input quadratic.

### Byte-aware cap-and-drop (no batching)

Pros: bounds module size simply. Cons: still lossy (drops mutants). Rejected in favor of lossless
batching; a residual byte/count cap may remain only as an extreme safety bound.

## Consequences

1. `runner.py` gains a strategy branch, a deterministic `_partition_opportunities_into_batches`, a
   per-batch generate/score loop, and a lighter between-batch cleanup that preserves stats/coverage.
2. Aggregation reuses `candidate_plan_counts` / `make_candidate_plan_id`; the plan fingerprint gains a
   partition signature so reruns stay comparable (ADR-001 rerun semantics preserved).
3. New config: `python_mutation_generation_strategy` (default `batch`) and
   `python_mutation_generation_max_generated_bytes` (8 MB). `maxSelected` unchanged, governs `hard_cap`
   rollback behavior.
4. Evidence (structured JSON, no DB migration) gains `generationStrategy`, `batchCount`, per-batch sizes,
   and `omittedByGeneratedBytesCap`.
5. CI cap-profile sampling, suppression, one-per-line selection, opportunity collection, and the Python2
   `mutmut==1.5.0` lane are untouched.
6. Performance: bounded per-batch overhead. Preserving `mutants/mutmut-stats.json` avoids Kx full stats
   collection across batches; `mutmut run` still performs per-batch clean/list-all/forced-fail checks.
   The win is turning an unbounded hang
   into ~10² s.
7. Rollout now defaults to `batch`; set `UTA_PYTHON_MUTATION_GENERATION_STRATEGY=hard_cap` for rollback.
